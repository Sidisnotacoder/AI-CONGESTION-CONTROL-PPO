Configure & Run Live Session

Build a real Mininet network with up to 4 sender devices sharing one bottleneck link, each running whichever policy you assign, and watch them genuinely compete for the link. Requires the live backend (sudo python3 dashboard/backend.py).

Heads up: a policy's own rate cap only ever limits its own sending rate — the bottleneck link itself is one shared, plain first-in-first-out queue with no built-in fairness between flows. That means a self-limiting policy (PPO) sharing the link with an uncapped one (Cubic) can end up with similar RTT but less throughput — restraint doesn't lower delay for everyone unless everyone restrains. The "Queue discipline" option below lets you try RED (a real Active Queue Management scheme) instead of plain FIFO; it does shift the throughput balance, though with Mininet's default RED thresholds it doesn't fully fix RTT at these bandwidths — try both and compare.

Live Multi-Flow Metrics

One card per active sender, updating in real time as the session streams — watch them share the bottleneck instead of viewing one arm at a time.

"Rate cap" is each sender's own self-imposed ceiling (what its policy controls); "Throughput" is what it actually achieved given everyone else's traffic. When throughput sits well below the rate cap, that sender isn't the one limiting itself — contention on the shared link is.

Live Control

Change the shared bottleneck while the session is running and watch every sender react in real time.

Flip queue discipline between plain FIFO and RED mid-session (same option as section 2, but live) and watch section 3's throughput numbers shift — a direct, real-time demonstration of how the queueing discipline itself, not just the policies, shapes who gets what share of a contended link.

Animated Topology Diagram

A picture of what's physically happening: line thickness follows each flow's rate cap, dash speed follows its measured throughput, and the bottleneck glows when it's congested. Works for a live session or for whatever you're scrubbing in section 1/7.

The queue-fill bar and glow reflect the worst RTT among the flows shown, not a direct packet count — Mininet doesn't expose live queue occupancy, so this is RTT used as a proxy for it, which is accurate directionally (higher RTT ⇒ fuller queue) even though the bar itself is illustrative, not a literal measurement.
